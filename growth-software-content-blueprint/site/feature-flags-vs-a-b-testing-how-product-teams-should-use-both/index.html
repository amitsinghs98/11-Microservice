Feature Flags vs A/B Testing: How Product Teams Should Use Both

Feature flags vs A/B testing comes down to control versus evidence: a flag decides who gets a change and lets you switch it off, while an A/B test randomly assigns users and measures whether the change moved an outcome. Most product teams need both, often on the same platform, but they answer different questions and need different discipline.

Should you use feature flags, A/B testing or both?

Use a feature flag whenever you need to control exposure, roll back fast or ship code before it's ready; use an A/B test only when you need a causal answer about an outcome. If you ship often and want to learn from releases, run both on a shared platform so experiments use the same targeting and assignment as your flags.

  • Engineering teams shipping daily with no experimentation programme yet: start with flags only, and add experiments when you have enough traffic and a metric owner.
  • Marketing teams testing website copy and layout: a client-side A/B testing tool may be enough; flags add little.
  • Product teams that want every significant release measured: a combined flag and experimentation platform.
  • Teams with low traffic: flags for safe rollout plus qualitative research; formal A/B tests will rarely reach a reliable result.

What is each one actually for?

A feature flag is a runtime switch in your code that decides which users see which variation, so you can release, target and roll back without redeploying. An A/B test is a research method that randomly splits eligible users between variations and compares a predefined metric to estimate the effect of the change.

The overlap is the assignment mechanism: an experiment needs a way to serve variation A to some users and B to others, and a flag is a convenient way to do it. The difference is intent. A flag rollout can target your beta customers first, which is useful for safety but useless as evidence, because those customers aren't a random sample. An experiment needs randomisation, a fixed metric, a planned sample and an analysis that accounts for chance.

How do feature flags and A/B tests compare?

Flags optimise for control and speed, and experiments optimise for valid conclusions. The table compares the two on the dimensions that cause confusion.

What does a flag-only release look like?

A flag-only release turns a feature on for staff, then a few customers, then everyone, watching operational health at each step. Nobody claims the feature improved a business metric, because nothing was randomised.

Hypothetical example: a team ships a new CSV import engine behind a flag. It enables the flag for internal accounts on day one, for ten design-partner customers in week one, then for 25%, 50% and 100% of accounts over the next fortnight, checking import errors and processing time after each step. When a large file causes timeouts at 50%, they switch the flag off in seconds, fix the bug and resume. Afterwards they remove the flag from the code.

When should a flag be a permanent kill switch?

Keep a permanent flag around any dependency that can fail in production, such as a third-party API, a costly background job or an AI feature with variable cost. A kill switch lets on-call engineers degrade gracefully instead of deploying a hotfix.

Hypothetical example: a product's AI summary feature calls an external model API. A long-lived operational flag disables summaries and shows a fallback message if the provider has an outage or spend spikes. This flag is never part of an experiment, has a named owner, and is documented in the runbook. Kill switches are the main legitimate exception to "delete flags once rolled out".

What does a properly randomised A/B test look like?

A real A/B test fixes the hypothesis, primary metric, eligible population and sample size before launch, assigns users at random and doesn't stop the moment the result looks good. It also checks that the split actually happened as planned.

Hypothetical example: a team believes a shorter onboarding checklist will raise the share of new accounts that reach their first report within seven days. It runs a 50/50 test on all new trial accounts for a pre-calculated duration, with a guardrail on support tickets. It uses a sample ratio mismatch check to confirm that both arms received the expected traffic; GrowthBook, for example, documents sample ratio mismatch checks in its experiment results; confirm the current behaviour in its docs. Only after the planned end date does it decide whether to ship.

Can you trust an A/B test that runs through feature flags?

Yes, provided the flag assigns users randomly and stickily, exposure events are logged at the moment users actually see the variation, and targeting rules aren't changed mid-test. Where does each approach fall short?

Flags fall short as evidence, because targeted rollouts confuse "the feature worked" with "we gave it to our best customers first". A/B tests fall short at low traffic, for long-term effects and for changes you can't randomise safely, such as pricing for existing contracts.

  • Flag debt: stale flags multiply code paths and make testing harder. Set an expiry and owner on every release flag.
  • Underpowered tests: a small B2B product may need months to detect a modest change. Use flags plus qualitative research, or test bigger changes.
  • Network effects: in collaborative products, users in different arms affect each other; randomise by account, not user.
  • Client-side flicker: browser-based A/B tools can briefly show the original before the variation, which server-side flags avoid. Our list of A/B testing software covers how each tool handles this.

How hard is it to combine or switch platforms?

Moving flags is mostly an engineering job: you replace SDK calls and recreate targeting rules, which is manageable with a wrapper around your flag calls. Moving experiments is harder because historical results, metric definitions and exposure data rarely transfer cleanly.

If you're starting fresh, wrap flag evaluation in your own small interface so the vendor can change later, and keep metric definitions in your warehouse or tracking plan rather than only inside the tool. For marketing-site tests run outside the product, a website experimentation platform can stay separate without harm.

What else do product teams ask about flags and experiments?

Most remaining questions are about overlap, traffic and tooling. Short answers follow.

Is a percentage rollout the same as an A/B test?

No. A percentage rollout limits exposure for safety; it becomes an experiment only if assignment is random and sticky, a metric is fixed in advance and the result is analysed properly.

How much traffic do we need for an A/B test?

It depends on your baseline conversion rate and the smallest effect you care about. Use a sample size calculator before launch; if the required duration is months, test a bigger change or use other evidence.

Should feature flags be evaluated on the server or the client?

Server-side evaluation avoids flicker and keeps targeting rules private, so it suits product logic. Client-side evaluation is simpler for front-end changes but can expose rules and cause flicker.

Do we need separate tools for flags and experiments?

Not necessarily. Several platforms combine both, which keeps assignment consistent; separate tools make sense when engineering and marketing run very different programmes.

What's the verdict on feature flags vs A/B testing?

Flags are infrastructure every shipping team should have; A/B tests are a research method you use when the question, traffic and metric justify it. Run experiments through flags when you can, but don't call a targeted rollout an experiment.
